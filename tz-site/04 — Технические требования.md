# 04 — Технические требования

← [[00 — MOC (карта ТЗ)]] · по скиллам `seo-audit`, `schema`, `ai-seo`

## Стек
- **Next.js (App Router)** — как в текущем превью. **SSR/SSG обязателен**: контент отдаётся в
  HTML до JS. Проверка: `view-source` каждой ключевой страницы содержит текст ответов.
- CMS: `⚠️ВРЕМЕННО: определить` (headless — Strapi/Payload/Sanity — под каталог/кейсы/рычаги/цены).
- Хостинг: Vercel (как сейчас).

## SEO/AEO-обязательное
- **Мета-слой на каждой странице:** уникальные `title` (вопрос+бренд+гео), `description`,
  Open Graph/Twitter, `canonical`, один `H1`. (Сейчас всё это отсутствует — см. `../site-snapshot/AUDIT-FINDINGS.md`.)
- **Schema.org (JSON-LD):** `Organization`+`LocalBusiness` (адрес/телефон/часы/гео),
  `Product`+`Offer` (оборудование, цена), `FAQPage`, `Article`, `BreadcrumbList`,
  `Review`/`AggregateRating` (рейтинг — с источником!), `ItemList` (сравнения).
- **`robots.txt`:** разрешить ИИ-ботов — `GPTBot`, `ChatGPT-User`, `PerplexityBot`,
  `ClaudeBot`, `anthropic-ai`, `Google-Extended`, `Bingbot`, `YandexBot`. Блокировать только training-only (`CCBot`) — если решим.
- **`sitemap.xml`** (авто) + **`/pricing.md`** (структурированные цены для ИИ-агентов).
- ⚠️ **`/llms.txt` — снят со статуса рычага.** Google прямо заявил, что не использует файл;
  Ahrefs на 137 000 доменов: 97% файлов не получили ни одного запроса, а среди полученных
  на ИИ-ботов пришлось 1.1%. Файл у нас лежит и вреда не наносит, но это поддержка ради
  ничего — устаревший `llms.txt` хуже отсутствующего. Разбор — `../audit/05-aeo-evidence-2026.md`.
- **`Article`, а не `QAPage`, на страницах ответов.** По спецификации Google `QAPage` — только
  там, где ответы присылают пользователи; у нас один авторский ответ. Было применено неверно,
  исправлено. `Article` заодно даёт `author` и `dateModified`.
- **301-редиректы:** со старых slug и с легаси-доменов (см. [[02 — Информационная архитектура]]).

## Что уже показано в прототипе (эталон разметки)
В `prototype/mimismart-v5.html` добавлен рабочий пример обязательного слоя — можно открыть
`view-source` и брать за образец:
- **Мета:** `charset`, `viewport`, `description`, Open Graph (`type`/`title`/`description`/`locale`),
  `twitter:card`. Заголовок переписан под запрос+бренд.
- **JSON-LD `Organization`** — только проверяемые факты: название, описание, `foundingDate` 2004,
  адрес и часы работы шоурума (Новоданиловская наб., 6к1). **`telephone` и `email` намеренно
  отсутствуют** — на текущем сайте это заглушки ([[99 — Открытые вопросы и временные допущения]]).
  Без них разметка `LocalBusiness` неполная: добавить сразу, как придут реальные контакты.
- **JSON-LD `BreadcrumbList`** — пример цепочки для вложенной страницы.
- **JSON-LD `FAQPage`** — строится скриптом **из тех же карточек-рычагов, что видит человек**
  (`#p-news .card` → `h3` = вопрос, `p` = ответ). Один источник правды: при правке текста статьи
  разметка не разъезжается, и это не «контент только для ИИ» (прямо запрещён в [[03 — Система 60 рычагов и контент-стандарт (AEO)]]).
  Проверено: 60 вопросов, валидный JSON, нет пустых полей.

### Измерено: что видит бот без исполнения JS
Отключил JavaScript и снял факты, чтобы срочность SSR обсуждалась цифрами, а не на словах:

| | без JS | с JS |
|---|---|---|
| Видимого текста | 732 знака | ~11 000 на главной |
| Видимых страниц | 0 (все `.page` скрыты до того, как JS добавит класс) | 1 |
| `<h1>` в документе | 17 (все страницы разом) | 1 на маршрут |
| `FAQPage` | **был пуст** → запечён статически, теперь 60 | 60 |
| `lang` | пусто (ставится из JS) | `ru` |

**Что исправлено прямо в прототипе:** `FAQPage` теперь запечён в HTML статически — бот без JS
видит все 60 пар вопрос-ответ. JS продолжает пересобирать его из видимого DOM, поэтому при правке
текста разметка не устаревает. Сверено: запечённая и рантайм-версии совпадают до знака.

**Что в одностраничнике не чинится и требует SSR:** 17 `<h1>` разом, 0 видимых страниц и пустой
`lang`. Это прямое следствие того, что все маршруты живут в одном файле и переключаются классом.

### Измерено под троттлингом (Slow-4G + CPU ×4, 390px)
Замеры с локального файла на быстрой машине ничего не говорят о реальном пользователе, поэтому
прогнал с замедлением процессора вчетверо и мобильной сетью:

| Метрика | Значение | Оценка |
|---|---|---|
| FCP | ~270 мс | хорошо |
| **CLS** | **0** | отлично — вёрстка не прыгает |
| domInteractive | ~870 мс | приемлемо |
| Длинные задачи | 3, максимум **~390 мс** | ⚠️ блокирует отзывчивость (INP) |

**Что показала локализация причины.** Разложил по слоям:
- без JS вообще — длинные задачи 71 и 75 мс (разбор и раскладка);
- с JS — добавляется задача ~375 мс;
- инструментированный прогон внутри скрипта: весь стартовый код отрабатывает за **~108 мс**.

Значит, основная стоимость — **разбор одного файла на 574 КБ** (HTML + инлайновый CSS + инлайновый
JS + 337 КБ base64-картинок), а не логика. Убирание картинок из файла дало 809 → 738 мс —
подтверждает: дело не в декодировании изображений, а в объёме единого документа.

**Что сделано:** индекс поиска переведён на ленивое построение — раньше он собирался при каждой
загрузке, хотя ищут единицы. Правильно по принципу «не платить всем за работу, нужную немногим»,
но на цифру это **не повлияло** (397 против 375 мс — шум). Записываю честно, чтобы никто не
считал это решённой проблемой.

**Что реально лечит:** вынос JS и CSS в отдельные кешируемые файлы, картинки файлами вместо
base64, разбиение на страницы через SSR — то есть Z10/Z12 из [[15 — ТЗ на доделки]]. В формате
одного самодостаточного файла эта задача не решается принципиально.

**Ограничение прототипа:** это одностраничник с hash-роутингом, поэтому мета и JSON-LD статичны и
общие. В продакшене на Next.js их генерируют **постранично** (свой `title`/`description`/`canonical`
и свой `Article` на каждый `/answers/{slug}`), причём **на сервере** — JSON-LD должен быть
в HTML до выполнения JS, иначе часть ИИ-ботов его не увидит.

## Производительность / a11y
- Core Web Vitals «good». Анимации — на GPU-friendly свойствах, ленивая загрузка, бюджет кадра.
- **`prefers-reduced-motion`** обязателен: полноценный статичный фолбэк (см. [[06 — Концепция анимации «Живое жилище»]]).
- Семантический HTML (`<main>/<nav>/<article>/<button>`), корректный accessibility tree,
  `alt` у изображений, таблицы/списки текстом (не картинками) — чтобы читали ИИ и агенты.
